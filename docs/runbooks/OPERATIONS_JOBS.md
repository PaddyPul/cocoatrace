# Scheduled operations and reviewed recovery

The API schedules five independent jobs after startup migrations. Pending evidence scans process at most five items per run; cleanup at most twenty; payment reminder generation and each email delivery batch at most twenty. Evidence jobs wait 60 seconds after completion; delivery jobs retain their 15-second interval. A slow job cannot overlap itself or block another job's loop.

A PostgreSQL session advisory lock serializes each scheduled job across API instances. Five dedicated lock connections avoid consuming the domain/request pool while provider work requires its own connections. Budget up to five additional PostgreSQL connections per replica. Use a direct/session-pinned PostgreSQL connection; transaction-mode poolers do not preserve session advisory locks. The existing per-object cleanup leases, scan lock and email outbox leases remain authoritative. SMTP is at least once: a crash after submission can duplicate mail.

Migration 036 introduced four bounded job-status rows; migration 051 extends the fixed job set with fee statement email and partial terminal-work indexes. Each run records start, completion, last success, a safe error code and consecutive failures. Missing, failed, never-successful or older-than-15-minute status is unhealthy. Disabled development email is `EMAIL_NOT_CONFIGURED`, not successful delivery; neither SMTP acceptance nor worker health confirms inbox receipt. Existing terminal cleanup/email rows keep reporting `TERMINAL_WORK_PENDING`, even when no new work was selected.

Platform administrators can open **Operations** in navigation, or `/operations`. Ordinary accounts have no controls and the API denies their reads and writes. The monitor explicitly reports unavailable/malformed reads and retains an unsaved recovery explanation during refresh. It shows the first fifty terminal cleanup records with an explicit more-records notice; processing reviewed records and refreshing exposes later records. It never returns object keys or recipient addresses.

`POST /operations/cleanup/:id/retry` requires a 10–500-character explanation, current platform `*` authority, a current session and fresh passkey assurance when required. The transaction locks current identity, permission, session and cleanup state, then requeues only a dead record and writes `operations.cleanup.retry` atomically. Repeated/concurrent requests cannot create duplicate transitions or audits. Live-reference, invalid-key and provider-mismatch failures refuse retry. Investigate these; do not edit the ledger to mark physical bytes deleted. A reviewed transient retry resets attempts and preserves byte/quota ownership until the existing worker physically deletes the object. Recovery does not directly delete evidence, clear safety holds, change trade quantities or release custody.

Hardened runtime status command (no npm inside API image):

```powershell
docker compose -f docker-compose.yml -f docker-compose.email-test.yml -f docker-compose.mfa-test.yml exec api node --import tsx api/scripts/operations-status.ts
```

A nonzero status means attention is needed, including suppressed email or first startup before all jobs have succeeded. Inspect safe job/error fields and the Operations page. Correct the storage/scanner/SMTP incident first. After a lock connection/database/status-write infrastructure failure the affected loop retires, emits a redacted error and its durable status becomes stale; restore the dependency and restart API to resume. Graceful shutdown immediately stops new scheduling and drains active jobs before closing the domain pool; the existing ten-second shutdown deadline still forces exit if a provider does not settle. Durable claims recover after expiry following forced exit.

Rollback: redeploy the previous API/web image; business queues, cleanup ownership and audits remain intact. Migration 036 is additive. Do not drop/recreate business data or manually remove private bytes to make monitoring green.

Remaining operations work: external alert collector/delivery and named incident owner; complete queue-backlog/DB/abuse metrics and thresholds; hosted scheduling/load and failure drills. These remain open under OPS-006/OPS-010; this slice does not close either broad item. There is no newly configured external alert service or real outgoing email provider.

## Reviewed terminal-email recovery

The Operations monitor includes separate **Payment reminder terminal email**, **Recall terminal email** and **Fee statement terminal email** sections. Each `GET /operations/email/:queue/dead` reads at most 51 rows using the existing partial terminal index, returns at most 50 ordered by ID, and explicitly reports additional records. Queue names are restricted to `payment_reminder`, `recall` and `fee_statement`. Reads require platform administrator authority and send `Cache-Control: no-store`; recipient addresses, user/business IDs, message content and raw provider errors are not returned. Unknown error text is mapped to `UNKNOWN_EMAIL_FAILURE`.

Correct the delivery incident first. Select **Review email retry**, review the duplicate-submission warning and enter a 10–500-character recovery explanation. `POST /operations/email/:queue/:id/retry` rechecks live administrator authority, active verified account/organization, current unrevoked session and fresh passkey assurance under the existing policy while holding transactional locks. A stale passkey triggers the existing verification flow. Failed verification, conflicts and monitor refresh preserve the explanation.

Only `failed_terminal` rows without a recorded submission or outstanding lease can be requeued. Sent, suppressed, queued, retrying and sending work cannot be recovered through this action. Inconsistent terminal records require investigation, not ledger edits. A row lock serializes competing decisions: one retry succeeds and a duplicate gets a conflict. Retry state and `operations.email.retry` audit (actor, queue, explanation, previous attempts and safe error code) commit together; audit failure rolls back recovery. Attempts reset to zero, next attempt becomes due, error/lease state clears and recall exhaustion clears. The original recipient, recall/reminder/fee identity, creation time and deduplication keys remain intact.

Recovery queues work; it does not send mail itself. Existing worker eligibility checks still apply, including payment state/recipient checks and inactive recall-recipient suppression. Recovery cannot acknowledge a recall, release retained stock or alter trade/payment state. SMTP remains at least once: a prior submission may have succeeded before a crash, even when no submission timestamp was recorded. Reviewed retry can therefore duplicate email. Worker success and SMTP acceptance do not prove inbox receipt.

Migration 051 adds the fee statement outbox and its due, sending-lease and terminal indexes; existing queues retain their original indexes. Roll back API/web images without deleting or rewriting outbox/audit records. The candidate's actual automated validation is in [the release handoff](../releases/TERMINAL_EMAIL_RECOVERY_WINDOWS.md). Full backlog metrics, external alerts, named ownership, real inbox and hosted drills remain separate acceptance work.

## Bounded queue backlog and incident visibility

`GET /operations/backlog` is platform-admin-only and read-only; it rejects query parameters and uses `Cache-Control: no-store`. One repeatable-read snapshot covers object cleanup, payment-reminder email, recall email and fee statement email. No recipient identity, object key, message, provider payload or record ID is returned. Evidence scan backlog is outside this endpoint; use its durable job status above until complete scanner signals are added.

Each queue uses indexed probes for queued/retryable, leased and terminal states, with a 1,001-row sentinel and displayed count capped at 1,000. `more=true` means a lower bound, not a full total. Retry/expired-lease observations cover the first 1,000 records in due/lease order. Oldest due time is the earliest scheduled attempt currently due, rather than creation time. Future scheduled attempts are not overdue. Suppressed/sent notifications and held/retained/done cleanup records are outside these active work states.

Incidents are fixed safe codes: `TERMINAL_WORK_PENDING`, `EXPIRED_LEASE` (including a missing sending lease), `OVERDUE_WORK` (scheduled attempt due for at least 15 minutes), and `MONITOR_LIMIT_REACHED`. A capped observation requires investigation even if work is not overdue. Counts indicate work, not confirmed delivery, malicious activity or a proven provider outage. The 15-minute threshold is an operator warning threshold, not a measured hosted SLO.

The monitor combines job status with these queue observations. A failed or malformed read clears the observation and marks it unknown; an open recovery explanation is retained. Database reads retain the existing 2-second statement and 5-second read deadlines. Failure returns HTTP 503 `OPERATIONS_BACKLOG_UNAVAILABLE` with no partial queue payload. The endpoint never claims work, extends a lease, requeues a record, releases quota or sends email.

Investigation order: inspect the queue signal and last job success, investigate provider/worker ownership, then use existing reviewed per-record recovery where eligible. An expired lease is evidence to investigate, not permission to mark delivery complete or release inventory. Refresh after recovery; monitoring failure must never be treated as zero backlog.

Migration 037 adds four partial indexes on notification due times and sending leases, including missing leases. It changes no records. Standard index creation can block queue writes during the migration; apply during a controlled API/worker restart. Existing object-cleanup due/lease and terminal register indexes are reused. Rollback drops only the four new indexes; revert the monitor code first. External alerts, incident ownership, scanner/DB/HTTP/abuse signals and hosted drills remain open; no paid provider or outgoing alert recipient is configured by this batch.


## Opt-in durable operator alerts

Migration 038 adds incident episodes, a per-recipient alert outbox and one polling-status row. Alerts default off. Set `OPERATIONS_ALERTS_ENABLED=true` and `OPERATIONS_ALERT_RECIPIENT_USER_IDS` to 1–5 distinct registered user UUIDs. Each target must remain active, in a verified unsuspended organization, with current wildcard platform-admin permission. Addresses are read from those accounts at submission, never accepted from a request. Configure SMTP through the existing adapter; alert SMTP timeout must be at most 10 seconds. Deployed environments require verified TLS. Synthetic demo mode prohibits alerts. Tests, stress fixtures and public demo preview explicitly disable them. Do not change APP_ENV to enable local capture: it also selects evidence namespaces.

The worker starts after 60 seconds and polls after each completed cycle plus 60 seconds. A dedicated PostgreSQL session lock and durable minimum one-minute interval serialize workers and the maintenance CLI across replicas. Enable only with a direct/session-compatible database connection; transaction-pooling proxies cannot preserve advisory session ownership. One additional coordination connection is used per enabled API process. Lost coordination stops that process's alert loop; investigate and restart it. Missing/stale status remains unhealthy. Existing scanner/cleanup/reminder/recall/fee-statement jobs retain their own ownership and scheduling.

One bounded repeatable-read observation covers the five job statuses and four queue probes. Signals are a fixed vocabulary: job failed/stale/not-observed; queue terminal/expired/overdue/capped; monitor unavailable. An ongoing signal has one open episode and one outbox row per configured eligible operator. Incomplete observations preserve old episodes. A complete observation resolves absent signals, and recurrence creates a new episode. Resolution means the signal was absent; it does not acknowledge an incident or release inventory or recall holds. No recurring reminder for the same continuous episode is promised.

Each cycle probes SMTP with handshake/authentication/QUIT without sending a message. A failed probe retains queued work without consuming delivery attempts. At most four submissions and four expired/invalid-claim repairs are handled per cycle. Claims use SKIP LOCKED, random five-minute leases and an eligibility/incident recheck under row locks immediately before SMTP. Retry delay is 60 seconds times the attempt count (capped at one hour); eight failures become terminal. A recorded submission timestamp prevents replay. A crash after SMTP acceptance but before commit can still duplicate a message: transport is at least once. Database uniqueness does not prove exactly-once email or inbox receipt.

Generic text contains only the safe signal, detection time and authenticated Operations link. It excludes customer records, commercial amounts, recipient lists, keys, tokens and provider error text. The endpoint `GET /operations/alerts` is platform-admin-only, rejects query parameters, returns no-store and omits recipient IDs/addresses and configuration fingerprint. The UI reports disabled, unknown, pending, terminal and failed/stale states explicitly. Current recipient eligibility and a configuration fingerprint prevent old successful observations from implying current configuration health. Poll and success timestamps must both be within 15 minutes and not in the future. These thresholds are investigation warnings, not a hosted SLO.

Operational history is stored in the incident/outbox tables, without inventing a human actor in audit_events. No HTTP delivery trigger or recipient override is supplied. Reviewed terminal-alert retry is documented in the separate recovery section below. Withdrawn/ineligible/resolved alerts are suppressed and never silently revived on later restoration. Development suppression is distinct from submission. Terminal or inconsistent submissions remain visible and require operator investigation. The reviewed recovery candidate below allows only eligible recognized delivery failures; inconsistent submissions remain refused. Do not hand-edit queue rows.

Use `node --import tsx api/scripts/operations-alerts.ts --operators` inside the API container to list up to five currently eligible accounts (private shell output). `--once` uses the same lock, cooldown and real configured delivery adapter; it is an actual delivery action when enabled. Disabled mode exits 1 without sending. Busy means another owner or the cooldown, not successful delivery. See the Windows handoff for optional Mailpit-only capture.

Disable the flag and recreate API to stop new alert cycles. Preserve incident/outbox history. Revert code before any schema rollback; the down migration refuses queued, sending, retryable or terminal alerts. New empty tables/indexes need no domain backfill. Physical deletion of completed alert history requires an agreed retention policy. A stopped API, broken database or broken SMTP path cannot reliably alert through itself: independent external monitoring, named incident owner, actual inbox receipt, scanner/HTTP/DB/abuse expansion and hosted failure/recovery drills remain open.


## Reviewed terminal operator-alert recovery

`GET /operations/alerts/dead` returns at most 50 terminal rows in stable UUID order with a 51-row sentinel. Candidate selection occurs before incident/recipient eligibility hydration. The snapshot read uses the existing two-second statement/five-second total catalog deadlines, rejects all query parameters and returns no-store. A failed read returns 503 OPERATIONS_ALERT_REGISTER_UNAVAILABLE without a partial register. Fields are record ID, terminal status, attempts, safe error code, creation time and current retryability. Recipient IDs/addresses, incident keys/IDs, lease credentials, text and provider diagnostics are omitted. Unknown error text is redacted.

`POST /operations/alerts/:id/retry` accepts only a trimmed explanation of 10–500 characters. Unknown body fields, malformed IDs and query parameters are refused. Existing platform-admin access, verified unsuspended organization, active account, live session and fresh passkey assurance are rechecked under locks inside the transaction. The terminal row is locked. It must have no recorded submission or lease and a recognized SMTP_SUBMISSION_FAILED or LEASE_EXPIRED error. INCONSISTENT_SUBMISSION and unknown error conditions remain investigation-only.

Alerts must currently be enabled and the original recipient UUID must still be configured. The same locked user/organization/role eligibility check is shared with actual delivery. The incident must remain open with an allowed safe signal. Disabled, withdrawn, resolved and suspended cases return conflict without requeueing or an audit event. A concurrent review can queue only once. Current worker eligibility remains mandatory after requeue; recovery is not a promise that the eventual submission will be authorized or delivered.

Successful review resets attempts/due time/error/lease state on the same outbox row and records operations.alert.retry with the reviewing actor, reason and previous attempts/safe code in the same transaction. Audit failure rolls back the state transition. It does not send directly, replace the recipient, reopen an incident, acknowledge a recall or release inventory/quota. SMTP remains at least once: unrecorded earlier acceptance can lead to duplicate mail. UI explanations survive refresh and refused recovery; failed/malformed observations clear the register instead of claiming it is empty.

No migration or new configuration is needed. Reverting this API/UI code removes the recovery action without rewriting existing outbox or audit history. The original operator-alert down-migration guard still applies. Configure local capture only through the earlier opt-in handoff; normal startup leaves alerts off. External inbox delivery, named ownership, independent monitoring, retention and hosted drills remain open. This candidate replaces the earlier runbook statement that no terminal-alert retry control is supplied; it does not mark runtime or external acceptance complete.

## Commercial fee statement delivery

The `fee_statement_email` job runs independently every 15 seconds after completion, with a maximum scheduled batch of 20. Its own advisory session lock prevents overlapping scheduled runs across replicas. It consumes durable `fee_statement_email_outbox` work committed with invoice issuance; repeated issuance does not create duplicate fee/recipient rows. Recipient eligibility is checked again immediately before SMTP. Only the current eligible payer contact receives commercial details; the private Operations monitor exposes safe state and error codes, never statement contents, addresses, payment references or provider diagnostics.

Investigate terminal submission errors before using the existing reviewed email retry flow with queue `fee_statement`. Live platform authority, session and fresh passkey assurance, a 10–500-character explanation and an atomic audit remain mandatory. Only terminal, unleased rows without a recorded submission can be requeued. Requeue does not move funds, waive a fee, unlock dispatch, mark an invoice paid or imply inbox receipt. The worker suppresses ineligible recipients or invoices rather than sending obsolete demands. Unknown SMTP failures remain redacted. A recorded submission is not replayed; an unrecorded provider acceptance after a crash can still produce duplicate mail because SMTP is at least once.

Fee refunds use their separate reviewed payer/independent-finance workflow, not email recovery. The recorded external refund reference is not a bank transfer; payer confirmation and cancellation checks remain independent. Neither email delivery nor refund recovery releases inventory or changes goods-payment records. The additional scheduled worker raises the lock-connection budget to five per API replica, plus the separate opt-in operator-alert coordination connection. Native runtime, hosted incident ownership and external inbox acceptance remain deployment checks.
