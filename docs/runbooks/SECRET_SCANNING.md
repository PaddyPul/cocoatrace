# Committed secret scanning

SEC-013 remains IN PROGRESS until CI runtime passes and repository settings are enabled by the owner. SAF-002 key rotation and owner-recorded revocation are separate.

`npm run check:secrets` runs Gitleaks8.30.1 using a pinned multi-platform GHCR image digest. It scans the complete history reachable from HEAD, including deleted files. CI checks out full history; shallow local clones fail with an explicit instruction. The release runner requires a clean committed tree, so uncommitted changes cannot masquerade as a scanned candidate. Standalone scanning covers committed history only. No npm dependency or paid scanner account is added. Upstream CLI semantics: https://github.com/gitleaks/gitleaks ; image/version reference: https://github.com/gitleaks/gitleaks/pkgs/container/gitleaks .

The scanner runs without network access inside its container, with a read-only repository mount. A temporary writable directory holds a fully redacted raw report; it is deleted before exit. The wrapper suppresses scanner stdout/stderr and persists only rule, file, line, fingerprint and accepted status. It does not serialize secret values, surrounding source, author or commit messages. The mandatory real canary generates a synthetic token in memory and requires the scanner to flag it before scanning the repository. Missing reports, incompatible native versions, scanner launch errors and malformed/expired review records fail closed. Inline allow comments and repository `.gitleaksignore` files do not bypass the gate.

Four historical fingerprints were reviewed: disposable integration/stress signing strings and one prose false positive. `security/secret-scan-exceptions.json` records exact occurrence fingerprints, reasons and2027-01-20 expiry. There are no broad path or test-directory exclusions. A new occurrence is a new review, even if its value resembles a test fixture. Expired exceptions fail even if their finding disappears; remove or re-review them explicitly. Never baseline unknown findings or grant a generic regex exception for convenience. Default upstream detection rules remain enabled through the explicit config.

For offline author diagnosis only, `GITLEAKS_BINARY` may identify an already installed binary; exact version8.30.1 is required and the same canary, rules, history and exceptions apply. Ordinary Windows instructions use Docker. Review and update the pinned image and version together for future scanner patches.

## Repository owner settings

In GitHub repository Settings, open the available code-security/secret-protection settings. Enable secret scanning and push protection where the repository/account supports them; review permitted bypass actors. Require the `secret-scan` check on protected main through the existing branch rules, keep pull requests and review requirements, and verify with a synthetic blocked-push exercise. Record the owner, date, availability and safe result without publishing test token values. These settings are not activated by this bundle and availability must be checked in the actual repository. Do not infer them from a green CI check.

On an actual finding, stop the release, restrict disclosure, identify the issuing system, revoke/rotate the credential and test revocation. Removing a file or rewriting history does not revoke credentials. Follow SECURITY.md and the private security-report runbook; do not paste raw findings into a public PR or issue. Share only the safe summary. A green regex scan is bounded detection evidence, not proof that no secret ever existed.
